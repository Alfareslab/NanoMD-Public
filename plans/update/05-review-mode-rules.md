## القاعدة الذهبية

> **بدل ما تسأل المطور أسئلة متفرقة في الشات — اكتب تقرير مراجعة منظم، احفظه كملف في المشروع، والمطور يرد عليك بالقرارات.**

## 1. متى تستخدم وضع المراجعة؟

| الحالة | استخدم Review Mode؟ |
|--------|---------------------|
| عندك **3 بنود أو أكثر** محتاج قرار فيهم | ✅ نعم |
| سؤال واحد بسيط | ❌ لا — اسأل في الشات |
| خطة تحتاج موافقة بند بند | ✅ نعم |
| تقرير audit محتاج ردود | ✅ نعم |
| اختيارات تصميم متعددة | ✅ نعم |

## 2. أوضاع المراجعة حسب السياق (Context-Aware Modes)

> الوكيل يحدد الوضع المناسب **تلقائياً** حسب طبيعة العمل الجاري:

| الوضع | الرمز | متى يُستخدم؟ | عمق الأسئلة | عدد البنود المتوقع |
|-------|-------|-------------|-------------|-------------------|
| **استكشافي** | 🔭 | تخطيط مشروع جديد / رؤية | عميق ومتشعب — يفتح آفاق جديدة | 10-20+ بند |
| **تطويري** | 🎯 | تطوير ميزة أو تحسين | محدد وواضح — يركز على التفاصيل | 5-10 بنود |
| **جراحي** | 🔧 | إصلاح مشكلة محددة | تشخيصي ومركّز — أقل أسئلة ممكنة | 3-5 بند |
| **تدقيقي** | 📋 | مراجعة audit أو فحص شامل | شامل وتغطية كاملة | حسب نطاق الفحص |

### سلوك كل وضع:

| الوضع | نوعية الأسئلة | هل يفتح مواضيع جديدة؟ |
|-------|-------------|----------------------|
| 🔭 استكشافي | أسئلة رؤية، نموذج عمل، مخاطر، بدائل | ✅ نعم — يقترح مواضيع المطور ما فكّرش فيها |
| 🎯 تطويري | أسئلة تصميم، اختيارات تقنية، أولويات | ⚠️ بحذر — فقط لو مرتبط مباشرة |
| 🔧 جراحي | أسئلة تشخيصية: إيه المشكلة، إيه الحل، إيه الأثر | ❌ لا — يركز على المشكلة المحددة |
| 📋 تدقيقي | أسئلة جودة، أمان، أداء، ديون تقنية | ✅ نعم — يغطي كل الجوانب |

## 3. حفظ ملف المراجعة (إلزامي)

> **كل تقرير مراجعة يُحفظ كملف في المشروع** — مش مجرد رسالة في الشات.
> **المكان: فولدر `reviews/` في جذر المشروع** — مكان واحد ثابت لكل الريفيوهات.

### المسار:

```
project-root/reviews/XX-review-[وصف].md
```

- **XX** = رقم تسلسلي (يكمّل من آخر رقم موجود في فولدر `reviews/`)
- **وصف** = وصف مختصر بالإنجليزية (kebab-case)

### أمثلة:

| السياق | اسم الملف |
|--------|-----------|
| عصف ذهني لمشروع | `reviews/01-review-business-model.md` |
| مراجعة تصميم | `reviews/02-review-navigation-flow.md` |
| مراجعة معمارية | `reviews/03-review-db-schema.md` |
| إصلاح مشكلة | `reviews/04-review-auth-bug.md` |

### القواعد:

| # | القاعدة |
|---|---------|
| 1 | الفولدر **`reviews/`** في جذر المشروع — لو مش موجود الوكيل **ينشئه تلقائياً** |
| 2 | الرقم التسلسلي يكمّل من آخر رقم موجود في فولدر `reviews/` |
| 3 | الملف يُحفظ **قبل** ما يعرض الرابط على المطور |
| 4 | القرارات تُحدّث في نفس الملف بعد رد المطور |
| 5 | الملف يبقى مرجع دائم — لا يُحذف بعد المراجعة |
| 6 | المرجع في **الهيدر** يربط الريفيو بالملف/الخطة الأصلية |

## 4. ملخص السياق (Context Header)

> كل تقرير مراجعة يبدأ بملخص سريع يوضح السياق:

```markdown
# 🔍 مراجعة: [العنوان]

> **السياق:** [ليه بنراجع ده — سطر أو اتنين]
> **الوضع:** [🔭/🎯/🔧/📋] [اسم الوضع]
> **المرجع:** [رابط أو اسم الخطة/الوثيقة المرتبطة — لو موجودة]
> **الأقسام:** [اسم قسم 1] (1–3) · [اسم قسم 2] (4–5) · [اسم قسم 3] (6)
> **عدد البنود:** [X] بند في [Y] أقسام
```

> **قاعدة الربط:** لو المراجعة مبنية على خطة أو audit أو وثيقة، الوكيل **لازم** يربطها في الهيدر.
> اسم ملف المراجعة يكون مرتبط باسم الخطة الأصلية مع توضيح.
>
> **خريطة الأقسام:** حقل `الأقسام` يعرض اسم كل قسم مع أرقام بنوده — كفهرس سريع.
> الأقسام تظهر في **الهيدر كخريطة** + اختيارياً **داخل الجدول كصفوف فاصل بصرية** (📌).

## 5. صيغة كتابة جداول المراجعة

> ⚠️ **التزم بهذه الصيغة بالحرف — NanoMD يعتمد عليها للكشف الأوتوماتيكي.**

### القاعدة الأساسية: صيغتين مدعومتين

> **كل بنود المراجعة تكون في جدول واحد.**
> NanoMD يدعم **صيغتين** — الوكيل يختار الأنسب:
>
> **ترتيب البنود:** البنود 🔴 الحرجة **تيجي الأول** في الجدول.

### الصيغة الأولى: 4 أعمدة (البند + التوصية مدمجين)

```markdown
| # | البند ← التوصية | التفاصيل | القرار |
|---|----------------|----------|--------|
| 1 | [🔴/🟡/🟢] [عنوان البند] ← [توصيتك] | [شرح تفصيلي] | |
```

### الصيغة الثانية: 5 أعمدة — Split Columns (مفضّلة)

> ✅ **الصيغة المفضّلة** — البند والتوصية منفصلين بصرياً في NanoMD.
> عند النسخ، NanoMD **يدمجهم تلقائياً** بعلامة `←` → نفس سلوك الصيغة الأولى.

```markdown
| # | البند | التوصية | التفاصيل | القرار |
|---|-------|---------|----------|--------|
| 1 | [🔴/🟡/🟢] [عنوان البند] | [توصيتك] | [شرح تفصيلي] | |
```

### صفوف الفاصل — Section Separators (اختياري)

> صفوف بصرية تفصل بين أقسام المراجعة **داخل الجدول**.
> تظهر كخط فاصل مميز مع عنوان القسم — بدون أزرار قرار.

**الصيغة:**

```markdown
| | 📌 اسم القسم | | | |
```

| القاعدة | التفاصيل |
|---------|----------|
| عمود `#` فاضي | NanoMD يكشف الفاصل تلقائياً |
| `📌` في عمود البند | رمز الكشف الإلزامي |
| بدون أزرار قرار | الفاصل مش بند — مش محتاج رد |
| مستثنى من النسخ | لا يظهر في نص النسخ |
| مستثنى من العداد | لا يتعد في عداد البنود |
| ألوان متبادلة | كل قسم ليه لون خلفية مختلف عن اللي قبله |

**مثال كامل مع فواصل:**

```markdown
| # | البند | التوصية | التفاصيل | القرار |
|---|-------|---------|----------|--------|
| | 📌 الأمان | | | |
| 1 | 🔴 صلاحيات الـ API | تشفير AES-256 | التفاصيل هنا | |
| 2 | 🟡 تسجيل الدخول | OAuth2 + JWT | التفاصيل هنا | |
| | 📌 الأداء | | | |
| 3 | 🟡 حجم الـ Bundle | Code splitting | التفاصيل هنا | |
```

### قواعد الأعمدة

| العمود | الوظيفة | مَن يكتبه؟ | يُنسخ مع الردود؟ |
|--------|---------|------------|-----------------|
| `#` | رقم البند (لتوافق NanoMD) | 🤖 الوكيل | ✅ نعم |
| `البند` | عنوان + مؤشر أولوية | 🤖 الوكيل | ✅ نعم (يُدمج مع التوصية بـ `←`) |
| `التوصية` | توصية الوكيل (اختياري — في الصيغة 5 أعمدة) | 🤖 الوكيل | ✅ نعم (يُدمج مع البند بـ `←`) |
| `التفاصيل` | شرح تفصيلي للسؤال أو الفجوة | 🤖 الوكيل | ❌ لا |
| `القرار` | رد المطور | 👤 المطور | ✅ نعم |

> ⚠️ **ترتيب الأعمدة حرج!** NanoMD بينسخ **البند + التوصية + القرار** ويتجاهل التفاصيل.
> لو غيّرت الترتيب — النسخ هيتكسر.
>
> في صيغة الـ 4 أعمدة: NanoMD بينسخ **العمود التاني** (البند ← التوصية) + **الأخير** (القرار).
> في صيغة الـ 5 أعمدة: NanoMD بيدمج **العمود التاني + التالت** بـ `←` + **الأخير** (القرار).

### قاعدة تفرّد البند

> ⚠️ **اسم كل بند لازم يكون فريد ومميز** — ممنوع بندين بنفس الاسم أو باسم يشبه اسم القسم.
>
> | ❌ غلط | ✅ صح |
> |--------|-------|
> | `🔴 تحديث README` | `🔴 جدول المراجع ناقص بروتوكولين` |
> | `🔴 تحديث README` | `🔴 شجرة protocols/ قديمة` |
> | `🟡 تحديث README` | `🟡 عدد الملفات الإجمالي غلط` |
>
> **القاعدة:** البند يوصف **المحتوى المحدد** — مش التصنيف العام.

### حدود الطول

| العنصر | الحد الأقصى | ليه؟ |
|--------|------------|------|
| عنوان البند | **45 حرف** | عشان سطر النسخ يفضل مقروء |
| التوصية | **60 حرف** | عشان سطر النسخ يفضل مقروء |

> **ما تغيّر عن v2.3:**
> - إضافة **صيغة 5 أعمدة** (Split Columns) — البند والتوصية منفصلين
> - إضافة **صفوف الفاصل** (📌) — فواصل بصرية داخل الجدول مع ألوان متبادلة
> - الأقسام ممكن تظهر في **الهيدر + الجدول** مش الهيدر بس
> - صيغة النسخ: `البند ← التوصية → القرار` (نفسها في الصيغتين)

## 6. مؤشرات الأولوية

> كل بند يبدأ بمؤشر أولوية يساعد المطور يرتب ردوده:

| الرمز | المعنى | الأثر |
|-------|--------|-------|
| 🔴 | حرج — يوقف الشغل | لازم قرار صريح — مينفعش يتأجل |
| 🟡 | مهم — يأثر على الجودة | يتأجل بحذر |
| 🟢 | اختياري — تحسين | آمن للتأجيل |

### القرار الذكي (Smart Default)

> البنود الاختيارية 🟢 **فقط** — لو المطور ماردش عليها، **التوصية تمشي تلقائياً**.
>
> البنود 🔴 الحرجة **لازم** رد صريح — مينفعش تتجاوز أبداً.

**في صيغة النسخ، لو المطور مردش:**

```
🟢 ألوان مخصصة ← تأجيل لبعد MVP → [افتراضي: ✅ تأجيل — التوصية]
🔴 صلاحيات الأمان ← تشفير AES-256 → ⚠️ بدون رد — محتاج قرار
```

## 7. أسماء الأعمدة المعتمدة (Auto-detect)

> NanoMD يكشف Review Mode أوتوماتيكياً لو العمود الأخير اسمه أحد الأسماء التالية **وقيمته فارغة**:

### أسماء عمود القرار (العمود الأخير — إلزامي)

| الاسم (عربي) | الاسم (إنجليزي) |
|-------------|----------------|
| القرار | Decision |
| الرد | Response |
| قرار المطور | Dev Decision |

### أسماء عمود التوصية (العمود الثالث — في صيغة 5 أعمدة)

| الاسم (عربي) | الاسم (إنجليزي) |
|-------------|----------------|
| التوصية | Recommendation |

## 8. الأزرار السريعة في NanoMD

عند كشف جدول مراجعة، NanoMD يضيف أزرار لكل صف:

| الزر | الرمز | ماذا يكتب في خلية القرار؟ |
|------|-------|---------------------------|
| موافق | ✅ | `✅ موافق` |
| رفض | ❌ | `❌ رفض` |
| تأجيل | ⏸️ | `⏸️ تأجيل` |

> بعد الضغط على أي زر، يمكن للمطور **إضافة تعليق** بجانب القرار.
>
> مثال: `✅ موافق — بس خلي اللون أغمق`

## 9. صيغة النسخ التلقائية (من NanoMD)

> **NanoMD بينسخ تلقائياً من الجدول — المطور مش محتاج يعمل حاجة يدوي.**
>
> لأن كل البنود في **جدول واحد** = **زر نسخ واحد**.
> ولأن التوصية **جوه عمود البند** = **النسخ متكامل**.

### صيغة النسخ التلقائية

```
البند ← التوصية → القرار
```

### مثال لنسخ NanoMD:

```
1. 🔴 جدول المراجع ناقص بروتوكولين ← إضافة review-mode و improvements للجدول → ✅ موافق
2. 🟡 عدد الملفات الإجمالي غلط ← تصحيح من 12 إلى 14 ملف → ✅ موافق — بس اتأكد من العدد
3. 🟢 مفيش فحص قبل حفظ المراجعة ← checklist من 3 نقاط → [افتراضي: ✅ تأجيل — التوصية]
```

### زر نسخ الردود (NanoMD)

| الحالة | شكل الزر |
|--------|----------|
| مفيش أي رد (0/N) | 🔘 رمادي — متعطل |
| بعض الردود (X/N) | 🟠 برتقالي — `⚠️ نسخ الردود (X/N)` |
| كل الردود (N/N) | 🟢 أخضر — `✅ نسخ الردود (N/N)` |

## 10. مثال كامل (من الوكيل)

> ده مثال لتقرير مراجعة كامل بالصيغة النهائية.
> الوكيل يحفظه كملف: `reviews/01-review-business-model.md`

```markdown
# 🔍 مراجعة: معمارية CodexShare

> **السياق:** بنحدد القرارات الأساسية لنموذج العمل وبنية التطبيق قبل كتابة الكود.
> **الوضع:** 🔭 استكشافي
> **المرجع:** `Docs/01-brainstorming/01-multi-tenant-vision.md`
> **الأقسام:** نموذج العمل (1–3) · الميزات (4–6)
> **عدد البنود:** 6 بنود في 2 أقسام

---

| # | البند ← التوصية | التفاصيل | القرار |
|---|----------------|----------|--------|
| 1 | 🔴 سعر الاشتراك السنوي غير محدد ← خطة واحدة كبداية | الرؤية بتقول "اشتراك سنوي" بس مفيش سعر ولا خطط | |
| 2 | 🟡 تجربة مجانية مش مذكورة ← Trial مجاني 14 يوم | مفيش ذكر لتجربة مجانية | |
| 3 | 🟢 مفيش حد لعدد الملفات ← 100 ملف أو 5GB لكل فني | مفيش حد لعدد الملفات أو الحجم | |
| 4 | 🔴 مدة صلاحية ملف العميل مفتوحة ← الفني يحدد 7/14/30 يوم | الملف له expires_at بس مفيش مدة محددة | |
| 5 | 🟡 Branding العميل محدود ← اسم + لوجو كافي للـ MVP | حالياً اسم الشركة بس | |
| 6 | 🟢 ألوان مخصصة لبوابة العميل ← تأجيل لبعد الـ MVP | ألوان الشركة في بوابة العميل | |
```

---

## 11. مثال الرد (من المطور — بعد النسخ من NanoMD)

```
1. 🔴 سعر الاشتراك السنوي غير محدد ← خطة واحدة كبداية → ✅ موافق — 200 دولار/سنة
2. 🟡 تجربة مجانية مش مذكورة ← Trial مجاني 14 يوم → ✅ موافق
3. 🟢 مفيش حد لعدد الملفات ← 100 ملف أو 5GB لكل فني → ⏸️ تأجيل
4. 🔴 مدة صلاحية ملف العميل مفتوحة ← الفني يحدد 7/14/30 يوم → ✅ موافق
5. 🟡 Branding العميل محدود ← اسم + لوجو كافي للـ MVP → ✅ موافق — بس خلي اللوجو اختياري
6. 🟢 ألوان مخصصة لبوابة العميل ← تأجيل لبعد الـ MVP → [افتراضي: ✅ تأجيل — التوصية]
```

> **لاحظ:** الرد متكامل — في كل سطر: البند + توصية الوكيل + قرار المطور.
> الوكيل يقدر يفهم القرار بدون ما يرجع للجدول.

## 12. فحص الجودة قبل حفظ المراجعة (Checklist)

> **الوكيل يفحص الـ 3 نقاط دول قبل ما يحفظ أي ملف مراجعة:**

| # | الفحص | التفاصيل |
|---|-------|----------|
| 1 | **تفرّد الأسماء** | كل بند ليه اسم فريد ومحدد — مفيش بندين بنفس الاسم أو باسم يشبه القسم |
| 2 | **حدود الطول** | عنوان البند ≤ 45 حرف — التوصية ≤ 60 حرف |
| 3 | **ترتيب الأعمدة** | العمود التاني (بعد #) هو `البند ← التوصية` — والأخير هو `القرار` |

> ⚠️ لو أي نقطة مش متحققة — **لا تحفظ الملف** وصلّح الأول.
